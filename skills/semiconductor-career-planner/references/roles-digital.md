# 数字 IC、FPGA 与 EDA 岗位路线

作者 / 品牌：我的模拟电路世界。内容核验日期：2026-09-22。

本文件是岗位能力库，按用户选定方向逐段读取，不要一次把六条路线全部布置给学生。它描述用于规划的典型职责与训练目标，不是对任何公司当季招聘门槛、岗位数量、薪资或录用结果的承诺。招聘要求应以学生目标城市、毕业年份及真实 JD 为准；没有 JD 时将岗位匹配结论标为“待核实”。

目录：0 共同基础与证据标准；1 digital-rtl；2 digital-dv；3 digital-pd-sta；4 digital-dft；5 fpga；6 eda-development；7 主线与辅线选择；8 来源与边界。路线对应总览中的 D1–D6。

## 0. 先用同一把尺子判断能力

### 0.1 等级与优先级

| 等级 | 能力定义 | 可接受的证据 |
|---|---|---|
| L0 | 未接触，或无法解释 | 明确记录空白，不能凭课程名称补分 |
| L1 | 能讲原理并完成基础题 | 独立画时序图、手算、口头解释，能回答追问 |
| L2 | 能参照文档完成最小实验并解释结果 | 可运行脚本、输入、版本、日志与对结果的解释 |
| L3 | 独立完成模块 / 实验、定位故障并提交可复现证据 | 从规格到验收的完整记录，含失败复现和修复 |
| L4 | 在约束下权衡 / 优化并经复核 | 对照实验、约束一致性、代价分析和他人复核；不等于资深工程师 |

P0 是目标岗位的基本能力优先项；P1 是求职区分度；P2 是方向拓展。下面的目标等级是学习建议，应结合真实 JD 调整。初级求职以核心 P0 达到 L2–L3、至少一项达到 L3 为起点，不要求所有内容达到 L4。听过课、看完视频、照抄代码、AI 生成结果均不能单独证明等级。

### 0.2 六条岗位的工作对象不同

| 路线 ID | 工作对象与主问题 | 应交付的主证据 | 容易混淆的边界 |
|---|---|---|---|
| digital-rtl | 微架构与可综合 RTL：功能如何以时钟周期实现 | 规格、RTL、约束、验证记录、综合与性能解释 | 会写 FPGA 例程不自动等于具备 ASIC 前端交付能力 |
| digital-dv | DUT 的行为与风险：哪些错误还没有被发现 | 验证计划、环境、检查器、覆盖率、缺陷闭环 | DV 不等于只看波形，也不等于只背 UVM 类名 |
| digital-pd-sta | 物理实现与时序：约束下如何布局布线并闭合 | SDC、PPA / 时序报告、实验记录、检查清单 | 跑出 GDS 不等于签核；STA 与 P&R 可为不同岗位 |
| digital-dft | 可制造测试结构：如何控制、观察和检测故障 | DFT 架构、scan / test 约束、故障与图样报告 | DFT 不等于功能验证，也不等于 ATE 产品测试 |
| fpga | 可编程器件与板级系统：硬件如何稳定运行 | RTL、XDC / SDC、实现报告、下载与板测记录 | FPGA 原型验证、算法加速、板卡开发各有不同侧重 |
| eda-development | EDA 软件：如何正确、高效处理电路与约束 | C++ / Python 代码、回归、算法说明、基准与性能剖析 | 会调用 EDA 工具不等于会开发 EDA 算法 |

### 0.3 所有数字路线共享的前置基础

按“先诊断、后补缺”执行，已有证据可跳过对应部分。建议合计 6–10 周、80–140 个有效小时，通常可与研一课程并行，不在后续方向路线中重复计时。

1. **数字电路，20–30 小时**：组合 / 时序、触发器、同步复位与异步复位、计数器、状态机、建立 / 保持时间。验收：给定波形手推下一周期状态；识别锁存器、组合环和优先级逻辑。
2. **HDL 与仿真，20–35 小时**：Verilog / SystemVerilog 基础、阻塞 / 非阻塞赋值、位宽与有符号数、参数化、可综合边界。验收：独立写一个带使能与复位的计数器和自检查 testbench；主动制造并定位一个 off-by-one 错误。
3. **Linux / Git / 自动化，15–25 小时**：目录与权限、进程、文本搜索、Git 提交、Python 文件处理、Make / shell 基础。验收：他人在新目录按 README 重跑实验；失败返回非零状态，而不是只打印“失败”。
4. **时序与数据接口，15–25 小时**：时钟周期、延迟与吞吐、ready/valid 握手、缓存、时钟域 / 复位域概念。验收：画出 backpressure 下数据保持和握手时刻；说清时序约束与 CDC 结构检查的分工。
5. **工程记录，10–25 小时**：规格先写、测试对照规格、固定随机种子、记录工具版本。验收：提交一张“需求 → 测试 → 日志 → 结论”映射表，任何结论都能回到文件。

学习材料与任务见 [resources-digital.md](resources-digital.md)。资源选择优先一门基础课、一份工具文档和一个正在做的项目；不要求先把整套书全部读完。

### 0.4 时间、验收和公开边界

- 以下周数按完成共同基础后、每周 12–18 小时实际排定任务估算；若净时间H只有12小时，则按0.8H约9.6小时排定并延长日历。小时区间反映基础与项目复杂度差异，不要求在较短周数内完成上限。项目三级可累积升级，不能将阶段学习工时与其中包含的项目工时重复相加；共同基础已通过的练习可压缩。
- 在排定的0.8H内部建议分配：理解原理25%、实现与实验50%、复盘和表达15%、岗位核对10%；另留0.2H缓冲。连续两周没有可运行产物，应缩小任务或补先修。
- 每个项目至少保存 `spec.md`、`README.md`、源代码、运行入口、版本清单、验收结果、`debug-notes.md`。具体文件名可按仓库规范调整。
- 验收应同时说明“测了什么、没测什么、在哪种条件下成立”。随机运行次数不是质量保证；覆盖率百分比必须列分母、不可达项、排除理由和工具配置。
- 公共 GitHub 仅放有发布权的自写 / 开源内容及合规脱敏记录。实验室 PDK、授权模型、商业工具安装包、企业 IP、实习数据、保密版图 / 网表不可因“求职展示”直接公开。
- 本文件中的频率、数据宽度、测试次数、项目规模都是**建议规格**，不是已实现结果。修改规格须先记录原因，不能通过降低约束掩盖失败。

## 1. digital-rtl：数字 IC 前端 / RTL 设计

### 1.1 适合度与实际交付

适合喜欢把问题拆成状态、流水线、数据通路与协议，愿意反复核对边界条件的人。可以暂缓选择的信号：只对界面操作感兴趣；无法接受周期级推演；长期回避调试；基础 HDL 练习后仍不愿查位宽 / 复位问题。以上是探索依据，不是按性格给人贴标签。

两周试做：用 15–25 小时实现一个带 backpressure 的 8 位、深度 4 同步 FIFO，并解释同时读写、空 / 满边界及复位行为。能从失败波形回到规格，且愿意继续做，是比“喜欢芯片”更有效的适配证据。

典型交付：模块规格与微架构图、端口 / 寄存器定义、可综合 RTL、基本断言、自测和协同 DV 的问题记录、综合脚本与约束假设、PPA / 时序初步解释、版本发布说明。校招应优先展示“一个模块独立做完整”，再扩展总线或处理器。

### 1.2 技能目标

| 优先级 | 技能 | 建议目标 | 实际验收证据 |
|---|---|---|---|
| P0 | 组合 / 时序、FSM、阻塞 / 非阻塞、位宽符号 | L3 | 自写参数化模块；解释综合出的寄存器 / 多路器；定位并修复两类真实错误或明确标注的教学注入，二者分列 |
| P0 | 从规格到微架构：吞吐、延迟、缓冲、仲裁 | L3 | 时序图、状态 / 数据通路图、资源与周期预算、取舍说明 |
| P0 | 自检查仿真与基本断言 | L3 | 独立参考模型、定向边界与随机回归；失败会自动退出 |
| P0 | 时钟 / 复位、CDC / RDC 基础 | L2 | 分别给出单 bit 电平、脉冲、多 bit 数据的方案与前提；说明同步器不能保证零风险 |
| P0 | 综合、基础 SDC、面积与关键路径 | L2 | 真实综合日志、无意外锁存器解释、时钟和 I/O 约束、时序报告逐段说明 |
| P0 | Linux、Git、Python / Tcl 基础 | L2 | 一条入口重跑回归，结果与代码提交可关联 |
| P1 | 一种目标接口：APB / AXI-Lite / AXI-Stream 等 | L3 | 依官方协议写检查项；包含等待、背压、错误 / 复位场景，不混用不同协议 |
| P1 | 流水线与 PPA 取舍、lint / 等价思想 | L3 | 在相同工艺 / 约束 / 版本下做两版比较，说明增加寄存器后的延迟变化 |
| P2 | 形式验证、低功耗 / UPF、缓存一致性、CPU / NPU 架构 | L1–L2 | 按目标 JD 选一个专题；提交范围明确的小实验，不要求同时学全 |

### 1.3 前置依赖与逐步路径

依赖关系：数字时序 → HDL → 自检查仿真 → FIFO / 流水线 → 协议模块 → 综合与 PPA；CDC 必须在单时钟正确后学习，多核 / 缓存一致性不能代替基本功。

| 阶段 | 周 / 小时 | 学什么、怎么练 | 出关条件 |
|---|---|---|---|
| 1 | 第 1–3 周，35–50h | 计数器、仲裁器、FSM；先画波形，再写 RTL；每日一个可运行小例子 | 能手推 10 个周期；没有无法解释的 lint 告警 |
| 2 | 第 4–7 周，45–65h | 同步 FIFO、参考队列、边界测试；练习先写规格和测试再实现 | FIFO 参数变更后仍通过；能现场复现一个修复 |
| 3 | 第 8–12 周，60–85h | 选择一种协议，写寄存器 / 流式接口与错误行为 | 验收表覆盖每条协议需求；接口等待和复位有证据 |
| 4 | 第 13–18 周，70–100h | 综合、时钟 / I/O 约束、关键路径定位；做一次流水线或资源复用比较 | 输出条件一致的面积 / 延迟 / 吞吐对照，不把估计频率说成硅片实测 |
| 5 | 第 19–26 周，90–125h | 核心项目整合、CDC 小实验、独立评审、面试表达 | 他人能复跑；15 分钟讲清规格、实现、故障、取舍与未完成项 |

### 1.4 三级项目

**最小项目：参数化同步 FIFO，25–40 小时。** 建议规格为 `DATA_WIDTH=8/16`、`DEPTH=4/8/16`，单时钟，明确 reset 优先级、满时写入 / 空时读取行为、同时读写规则。验收：对每个配置覆盖空、满、回绕、同时读写、操作中复位；参考队列逐事务比较；不少于 10 个固定种子、每个 1000 次操作作为起始预算，发现新风险后补定向测试。失败诊断：先区分采样竞态、指针回绕、计数器位宽和规格歧义。公开证据：规格、RTL、测试、种子、精简日志和一次故障修复 diff。随机通过不能取代边界测试。

**核心项目：带寄存器配置的流式数据处理模块，90–150 小时。** 建议 16 位输入，选择累加 / 饱和加法 / 简单 FIR 之一；接口采用明确定义的 ready/valid，配置侧选 APB 或 AXI-Lite 之一；说明运算位宽、溢出策略、背压、帧界限和配置生效时刻。验收：Python 参考模型、随机停顿、不连续输入、最大 / 最小值、配置中断、运行中复位；记录无停顿吞吐与延迟；综合并解释最差路径。失败诊断：检查有符号扩展、valid 与数据错拍、配置与在途事务一致性、组合 ready 环。公开证据：需求追踪表、架构图、回归、综合脚本、固定条件结果，不发布受限单元库。

**进阶项目：核心模块的架构取舍或小型子系统，100–180 小时。** 两选一：同一运算做全流水与资源复用两版；或加入一个异步 FIFO 完成双时钟传输。验收：保持同一功能规格和测试集，列出吞吐、延迟、寄存器 / 单元面积及假设；双时钟版本扫描多个频率比和相位，补结构 / 约束审查。失败诊断：区分算法等价、时序违例、跨域协议错误；数字仿真无法证明亚稳态失效率。公开证据：比较表、约束审查、反例与修复；仅在实际完成时写“形式验证 / CDC 工具检查通过”。

### 1.5 面试与常见误区

推荐问题与合格回答线索：① 非阻塞赋值为何适合时序逻辑，能否画出反例；② 延迟 4 周期是否意味着每 4 周期才能接收一次数据；③ FIFO 满且同时读写时到底接受哪个操作，答案必须服从规格；④ 多 bit 总线为何不能每 bit 各接两个触发器；⑤ 如何判断综合后面积变化来自架构而非不同约束；⑥ 请现场解释自己项目最难定位的错误及其测试缺口。

常见误区：从大 CPU 开始导致所有模块都只会复制；把 `#delay` 当作可综合延时；关掉全部告警；只看“波形像对的”；用假路径隐藏真实同步路径；简历写“精通 AXI”却未处理独立通道与背压。

无商业 EDA 时：用 Verilator / cocotb 做功能实验、Yosys 做适配语法的综合、OpenSTA / OpenROAD 学习时序与实现。须注明所用前端支持的 SystemVerilog 子集；不能据此声称已完成公司商业 lint、CDC / RDC、形式等价、低功耗或签核流程。对应官方入口见资源 D2、D3、D5、D6。

## 2. digital-dv：数字 IC 设计验证

### 2.1 适合度与实际交付

适合喜欢找反例、建立模型、追踪原因，愿意读规格和别人的代码的人。暂缓信号：只追求“测试通过”，不愿解释覆盖缺口；对随机测试失败没有耐心；认为验证不需要数字电路知识。两周试做：拿已知规格的 FIFO，先不改 RTL，用独立参考队列写边界测试，主动注入 3 种 bug；验收看测试能否抓住错误，而不是 testbench 行数。

典型交付：验证计划、需求到测试 / 覆盖点映射、driver / monitor / scoreboard / reference model、断言、受约束激励、回归与覆盖分析、可复现缺陷报告、模块 / 子系统验证收尾记录。UVM 是方法与复用框架，验证思维、协议理解和调试能力是更前置的能力。

### 2.2 技能目标

| 优先级 | 技能 | 建议目标 | 实际验收证据 |
|---|---|---|---|
| P0 | 数字电路、RTL 阅读、周期与并发语义 | L2–L3 | 给陌生模块画时序图；定位阻塞 / 非阻塞与采样时刻错误 |
| P0 | 验证计划、风险分析、正反场景 | L3 | 每条需求至少一个检查方法；说明未覆盖风险 |
| P0 | SystemVerilog 验证基础或可运行的过渡验证环境 | L3 | transaction、driver、monitor、scoreboard 职责分离；独立参考模型 |
| P0 | 自动比较、断言、超时与复位处理 | L3 | 错误自动失败，挂死可被发现；有断言触发与定位证据 |
| P0 | 随机回归、覆盖率与缺陷闭环 | L3 | 保存种子、分类失败、解释覆盖分母；缺陷有重现步骤和关闭依据 |
| P0 | Linux / Git / Python、日志分析 | L2 | 一条入口运行多配置回归；提取首个因果错误而非最后一行报错 |
| P1 | UVM 组件、phase、sequence、TLM、factory / config | L2–L3 | 在受支持的仿真器上跑通可复用 agent；修改 DUT 配置后不整套重写 |
| P1 | SVA / 形式验证、协议 / 寄存器模型 | L2–L3 | 能区分假设与断言；证明 / 有界检查的条件、深度、反例明确 |
| P2 | SoC、低功耗验证、混合信号、性能验证 | L1–L2 | 依据目标 JD 选一项，不把术语清单当掌握 |

若目标 JD 明确要求 SV/UVM，P1 中的 UVM 应上调 P0；Python / cocotb 项目是可验证的起点，不能在简历中直接改名为 UVM 项目。

### 2.3 前置依赖与逐步路径

依赖关系：RTL 和时序 → 自检查测试 → transaction / scoreboard → 覆盖与随机 → UVM 复用 → 子系统；先能解释一个丢包，再学复杂 factory 覆盖。

| 阶段 | 周 / 小时 | 学什么、怎么练 | 出关条件 |
|---|---|---|---|
| 1 | 第 1–3 周，35–50h | 从规格导出等价类 / 边界；做不依赖 UVM 的自检查环境 | 对已知错误有失败证明，正确版通过 |
| 2 | 第 4–7 周，45–65h | driver / monitor / scoreboard 分工、并发、超时、复位清理 | 被动 monitor 不根据激励“猜”输出；reset 后旧事务处理明确 |
| 3 | 第 8–12 周，60–85h | SV 类 / interface / 随机约束、覆盖与基础断言 | 覆盖缺口能转化成新测试；清楚当前模拟器限制 |
| 4 | 第 13–18 周，70–100h | 有合适工具时移植到 UVM；无工具先完成模块边界和接口文档 | agent 可在另一配置复用；未运行的 UVM 代码标为待验证 |
| 5 | 第 19–27 周，100–145h | 核心协议 DUT、故障注入、回归分类、验证报告 | 同伴植入的规格违例能被发现；完成 3 个缺陷闭环故事 |

### 2.4 三级项目

**最小项目：FIFO 破坏性测试，25–45 小时。** 规格沿用明确的单时钟 FIFO，RTL 可以是自写或注明许可证的开源模块。验收：空满、回绕、连续流、reset、同时读写；至少注入“满标志提前、读数据错拍、指针回绕错误”三类独立 bug，并记录每类被哪条检查捕获。失败诊断：先检查参考模型是否照抄 DUT 实现、输入采样点是否正确、异常是否被测试框架吞掉。公开证据：测试计划、通过版 / 故障版或补丁、失败日志、缺陷表。

**核心项目：APB 寄存器模块或 AXI-Lite 从设备验证，90–160 小时。** 初学者选一个协议，不一次混做；明确地址空间、访问权限、等待 / 响应、byte enable（协议适用时）、错误地址和复位。验收：transaction 驱动、被动 monitor、独立寄存器参考模型、协议断言、定向与随机测试；覆盖操作 × 地址类型 × 等待条件 × 复位交互；对不可达交叉覆盖给理由。失败诊断：区分 DUT 缺陷、环境竞态、参考模型错误、规格不清；写最小复现而非上传整段回归日志。公开证据：架构图、覆盖定义与实际结果、至少3类可复现的失败或明确标注的教学故障注入案例，进阶可扩到5类。真实缺陷与注入案例分列；数量是练习范围，需求覆盖、独立检查、复现与修复验证才是主要验收。

**进阶项目：复用 agent 验证子系统，100–180 小时。** 选带配置、FIFO、运算核的双接口子系统；合适环境下用 UVM agent / sequence / scoreboard，也可在资源不足时保留非 UVM 实现并列迁移计划。验收：多配置重用、并发流与 backpressure、运行中复位、长时间挂死检测；覆盖收敛有需求映射；对关键不变量做断言或范围明确的形式检查。失败诊断：查事务关联 ID、队列生命周期、reset 竞争、激励合法性及假设是否过强。公开证据：回归 manifest、工具版本、覆盖排除审查、故障定位录像；不能把 Python 功能计数器写成“完整 SV covergroup 覆盖闭合”。

### 2.5 面试与常见误区

问题与回答线索：① monitor 为什么应独立于 driver；② code coverage 与 functional coverage 各说明什么，为什么 100% 也不能证明无 bug；③ random seed 复现失败还需要哪些版本 / 配置；④ UVM objection 用来解决什么，滥用会怎样；⑤ reset 到来时 scoreboard 如何处理在途事务；⑥ assertion 与 assumption 混用如何制造“证明通过”；⑦ 用自己的缺陷报告演示根因与症状的差别。

常见误区：先背完整 UVM 再做第一个 testbench；只做合法连续传输；照 DUT 算法复制参考模型；追数字覆盖率却无需求映射；把 bug 数当能力分数而隐去故障注入性质；把随机百万次当形式证明。

无商业 EDA 时：cocotb + 支持的仿真器可以训练验证架构、自动比较、覆盖规划与回归。Verilator 对类、断言和功能覆盖的支持随版本变化，必须先用小实验核对需要的特性；不能概括成“全部支持”或“完全不支持”。UVM 文档与参考实现可公开获得，但框架可下载不等于本机可运行。若缺少兼容环境，SV/UVM 项仅计 L1 或明确的局部 L2，争取学校合法环境补齐。来源见 D2、D3、D4。

## 3. digital-pd-sta：数字物理设计 / 静态时序分析

### 3.1 适合度与实际交付

适合喜欢约束、空间关系、定量实验和长日志分析的人；需要愿意理解标准单元、互连、时钟树以及工具为何做出某个选择。暂缓信号：只想点击“自动完成”；不愿追溯时序报告中的约束；认为后端不用读 RTL。两周试做：在小型教学设计上读懂一条 setup 与一条 hold 路径，修改一个合理约束并预测后果，再用工具核对。

PD 交付常含 floorplan、供电规划、placement、CTS、routing、ECO、检查和交接报告；STA 交付更侧重时钟 / I/O / 例外约束、模式与角点、时序路径审查、违例定位及跨团队闭合。先共享基础，再按 JD 分支，不要求一个研一学生同时达到两个岗位的所有深度。

### 3.2 技能目标

| 优先级 | 技能 | 建议目标 | 实际验收证据 |
|---|---|---|---|
| P0 | 数字时序、setup / hold、skew / latency / uncertainty | L3 | 手算路径与工具报告一致；说明符号和发射 / 捕获边沿 |
| P0 | SDC：clock、generated clock、I/O、例外约束 | L3 | 约束说明书；列出未约束端点、例外依据与审查结果 |
| P0 | Liberty / LEF / DEF / 网表 / SPEF / SDC 的作用 | L2 | 一张输入输出依赖图；确认单位、角点、库与网表匹配 |
| P0 | Tcl、Linux、结果提取与配置管理 | L3 | 多配置实验自动汇总，报告能回到命令和版本 |
| P0 | P&R 流程与常见拥塞 / 时序问题 | L2–L3 | 小设计完成指定流程；每阶段日志与失败分析；STA 方向可先达 L2 |
| P0 | 约束完整性与证据边界 | L3 | 不用删除路径 / 乱加 false path 消除违例；明确未做的签核项目 |

| P1 | DRC / LVS、antenna、IR / EM 概念与报告阅读 | L2 | 区分工具内检查、教学规则检查和获准签核规则；列出实际执行项目 |
| P2 | OCV / AOCV / POCV、SI、低功耗多电源域、先进封装 | L1–L2 | 按目标岗位选读；无相应模型时不造数值结果 |

### 3.3 前置依赖与逐步路径

依赖关系：触发器时序与互连 RC → 库 / 约束 → 单路径 STA → 多路径与约束审查 → P&R / CTS → 多场景 / ECO；不能从“WNS 是正数”跳到“设计可流片”。

| 阶段 | 周 / 小时 | 学什么、怎么练 | 出关条件 |
|---|---|---|---|
| 1 | 第 1–4 周，45–65h | 单路径手算、Liberty / SDC 阅读、OpenSTA 教学例子 | setup / hold 各解释一条完整路径，核对单位 |
| 2 | 第 5–8 周，45–65h | clock、I/O、generated clock、未约束路径与合理例外 | 给另一人审查约束；能发现故意漏掉的时钟 / 端口 |
| 3 | 第 9–14 周，70–100h | 用公开平台完成小设计 P&R，逐阶段看面积 / 拥塞 / 时序 | 能解释 CTS 前后变化、寄生估计与提取的区别 |
| 4 | 第 15–21 周，85–120h | PD 分支练 floorplan / 密度 / CTS；STA 分支练多场景报告与 ECO | 至少一组可解释的优化与基准对照；若有真实失败则复盘，无失败可另做标明的教学注入 |
| 5 | 第 22–30 周，110–155h | 核心项目整理、复核异常路径、证据包与面试 | 输入、约束、日志、结果能追溯；签核边界逐项写清 |

### 3.4 三级项目

**最小项目：时序路径实验册，30–45 小时。** 用公开库与 10–100 个寄存器的自写小网表，分别创建组合逻辑长路径、短路径与受控分频时钟示例。验收：手算与工具结果差异可解释；展示漏约束如何导致误判；合理加入时钟 / I/O 约束后重新分析。失败诊断：先查时间单位、库、时钟对象匹配和网表连接，再查算法 / RC。公开证据：微型网表、SDC、手算表、完整路径报告和约束审查记录。

**核心项目：小模块 RTL 到布局布线的学习闭环，100–170 小时。** 选 1,000–10,000 单元量级的教学模块作为起始范围，具体规模依机器资源调整；固定公开工艺平台、库角点、版本、频率目标、面积上限。验收：记录综合、floorplan、place、CTS、route 的结果；列出 setup / hold、未约束路径、工具内 DRC 与实际完成的版图检查；记录真实拥塞 / 时序检查结论；如有问题则保存修复过程，若全部通过可另做明确标注的教学故障注入，不强求原设计出现问题。失败诊断：按首次异常阶段查 floorplan / 密度、长连线、时钟约束、宏块 / 引脚布局和单元可用性，不能只改最后一步。公开证据：配置与脚本、阶段报告、关键路径图、失败前后对比；GDS 可公开与否由源库许可证决定。

**进阶项目：三因素受控 PPA / 时序实验，100–180 小时。** 从密度、时钟周期、RTL 流水线、placement seed、CTS 参数中选三项，每次明确控制变量；STA 分支可改为相同设计的多模式 / 多角点约束审查。验收：至少 6 组配置，每组可复跑；比较面积、关键路径、WNS / TNS、hold 与运行时，报告失败配置；说明比较基于估计 RC 还是提取寄生，是否可比。失败诊断：排除版本、库、约束、随机性和报告阶段变化；不能只挑最好一组。公开证据：实验矩阵、原始摘要、自动汇总脚本、trade-off 解释和未签核项。

### 3.5 面试与常见误区

问题与回答线索：① 为什么降低频率通常不能解决 hold；② 正 skew 对 setup / hold 分别可能有什么影响；③ false path 与 multicycle 各需要什么设计依据；④ ideal clock 与 propagated clock 的报告差别；⑤ WNS 合格但还有未约束路径为什么不能下结论；⑥ 为什么提高密度可能同时影响面积、拥塞和时序；⑦ 一个 ECO 改好了最差 setup 后还要检查什么。

常见误区：把 LEF 和 GDS 混为同一用途；只看 WNS 不看 hold、TNS、路径覆盖与检查项；用任意 multicycle 放松关键路径；比较不同 PDK 的“先进程度”；教程跑出 GDS 就写“完成流片 / signoff”。

无商业 EDA 时：OpenSTA 能学习网表、Liberty、SDC、SPEF 与时序报告；OpenROAD Flow Scripts 可用于公开平台的实现实验。课程结果须按实际工具、规则、角点、输入模型描述。**开源并不意味着天然不能流片，商业软件也不意味着自动签核；本训练项目没有执行目标代工厂 / 公司认可的完整签核流程时，就不能声称具备商业签核结果。** 未完成 SI、OCV、EM / IR、物理验证、可靠性或多场景检查的部分逐项标为缺口。来源见 D6、D7。

## 4. digital-dft：可测性设计 DFT

### 4.1 适合度与实际交付

这里的 DFT 是 Design for Test，不是密度泛函理论。适合愿意在设计、验证、后端与测试之间协调，喜欢故障模型、结构约束和系统排查的人。暂缓信号：只想写功能 RTL；对时钟 / 复位和制造测试没有兴趣；以为“跑通 scan shift”就已完成 ATPG。

两周试做：用 8–16 个触发器建立一条手写 scan chain，分别跑 shift 与 capture；注入一个固定故障并说明如何激活和观察。能清楚区分“设计功能正确”和“某类故障可检测”后再决定主线。

典型交付：测试模式 / 架构说明、scan 插入与链报告、test clock / reset / enable 约束、DFT 规则问题闭环、ATPG 与故障分类、图样验证、与后端及测试团队的交接。压缩测试、MBIST、JTAG / IJTAG、at-speed 是不同专题，应按目标 JD 选择。DFT 工程师与产品 / ATE 测试工程师协作紧密，但工作边界不同。

### 4.2 技能目标

| 优先级 | 技能 | 建议目标 | 实际验收证据 |
|---|---|---|---|
| P0 | 数字逻辑、时钟 / 复位与 scan shift / capture | L3 | scan 波形、模式切换测试、功能模式回归 |
| P0 | 可控制性 / 可观察性、stuck-at 故障模型 | L3 | 为小电路手工生成检测向量，解释不可检测故障 |
| P0 | scan 链结构与基础 DFT 规则 | L2–L3 | 链长度 / 连接检查，定位不可控时钟、复位或未知值来源 |
| P0 | ATPG、故障仿真、fault coverage 的分母 | L2 | 真实或教学故障列表、分类、检测矩阵；不混淆故障覆盖和功能覆盖 |
| P0 | 基础 STA、测试时序约束与图样验证 | L2 | 分别描述 shift / capture 约束和模式；说明工具是否真的做了时序分析 |
| P0 | Tcl / Python / Linux、日志与报告处理 | L2–L3 | 自动统计链 / 故障结果，回到输入和具体检查项 |
| P1 | transition fault、at-speed / OCC、X 管理 | L2 | 在有资源时做限定范围实验；无资源用清楚标注的原理推演 |
| P1 | MBIST 或 JTAG / IJTAG 或 scan compression | L2–L3 | 选择一项做完整小项目，其他保持 L1 |
| P2 | 层次化 DFT、测试功耗、诊断 / 良率、先进封装测试 | L1–L2 | 结合目标行业 / 公司阅读和案例讨论，不强求教学项目覆盖 |

### 4.3 前置依赖与逐步路径

依赖关系：触发器 / 时钟复位 → scan 结构 → 故障模型 → 故障仿真 / ATPG → 测试时序 → 压缩 / MBIST 专题。若缺少合法商业 DFT 环境，先把岗位评估列为“理论与教学实验可推进，工程工具链证据待补”，不要让学生误以为资源限制不存在。

| 阶段 | 周 / 小时 | 学什么、怎么练 | 出关条件 |
|---|---|---|---|
| 1 | 第 1–4 周，45–65h | scan 单元、shift / capture、链与功能模式切换 | 能逐拍解释链内状态，功能模式不受影响 |
| 2 | 第 5–8 周，45–65h | 小组合电路 stuck-at 故障、穷举故障仿真 | 独立计算故障检测矩阵，清楚 collapsed / uncollapsed 分母 |
| 3 | 第 9–14 周，70–100h | scan 插入或受限教学替代，链检查与测试约束 | 清楚已执行哪些规则 / 模式，能定位一类结构问题 |
| 4 | 第 15–21 周，85–120h | 有环境则做 ATPG / pattern 验证；无环境做教学 ATPG + 明确缺口 | 覆盖率与故障类别可追溯，不把教学结果称为产品覆盖率 |
| 5 | 第 22–30 周，110–155h | MBIST / JTAG 专题、岗位对齐、缺陷与交接报告 | 一个专题完整闭环，能说明与 RTL / PD / ATE 的交接点 |

### 4.4 三级项目

**最小项目：手写 scan chain 与故障激活，25–45 小时。** 建议 8–16 bit、单测试时钟，明确定义 `scan_enable`、`scan_in`、`scan_out`、复位策略和 shift / capture 时序。验收：移入与移出匹配、不同初始状态、模式切换、功能模式等价的限定测试；解释一个故障为何无法仅靠某个输入向量观察到。失败诊断：scan 位序、采样边沿、enable 切换时刻、异步 reset 活跃。公开证据：电路图、波形、测试与解释。手写 scan 不可称为“使用工业工具完成 scan 插入”。

**核心项目：小网表的教学 ATPG / 故障仿真，90–150 小时。** 从不超过 8 个主输入、20–100 个门的组合电路开始，采用**单固定故障 stuck-at**，明确故障位置集合；用 Python 穷举输入、输出 good / faulty 比较矩阵，贪心选取测试集；再把 scan capture 的组合核加入学习。验收：至少两个人工可算例子交叉核对；保存 detected、undetected 与已证明 redundant 的区别；报告原始 / 折叠故障数、测试集大小与运行时。失败诊断：故障注入点错误、扇出分支与 stem 混淆、并行故障状态污染、把“未找到”误判“不可检测”。公开证据：自写网表、算法、检测矩阵、边界声明。该项目证明原理与软件实现，不能替代工业 ATPG、transition fault、压缩测试或 ATE 图样交付经验。

**进阶项目：教学 MBIST 或合法工具链 DFT 闭环，100–180 小时。** 二选一。A：自写 32×8 bit SRAM 行为模型与 March 类教学序列控制器，列清所采用算法的操作序列和可检测故障模型，注入 stuck-at / 指定 transition / coupling 的明确子集。B：在导师允许的合法环境中对小模块执行 scan 插入、DRC、ATPG、pattern simulation 与测试模式时序审查。验收：A 逐一证明所声明的注入故障能被捕获，说明行为模型不覆盖真实存储器物理缺陷；B 保存实际工具和授权范围内报告，故障分类 / 模式 / 分母一致。失败诊断：A 查地址遍历、读写时序、期望值更新、模型是否真的表达了故障；B 查 X 来源、模式约束、链连接与时钟 / reset 可控性。公开证据：可发布代码、算法 / 模式说明、脱敏结果；有 NDA 时仅做经过许可的抽象方法描述。

### 4.5 面试与常见误区

问题与回答线索：① scan 为什么改善可控制性和可观察性；② shift 与 capture 分别在做什么；③ fault coverage 与 test coverage 在所用工具里的定义为何必须查清；④ 不可检测故障与未检测故障的差别；⑤ 异步 reset 为何可能破坏测试；⑥ transition fault 为什么不能简单等同于 stuck-at；⑦ scan 链越多对测试时间、引脚、功耗和布线有何影响。

常见误区：把 DFT 当作背术语小众捷径；只跑功能测试就声称故障覆盖；用教学穷举替代工业 ATPG 后不说明规模边界；写“100% 覆盖”却删除难测故障；认为所有 March 序列都覆盖所有存储器故障。

无商业 EDA 时：可以手写 scan、故障模拟器、教学 ATPG 和 MBIST；OpenROAD DFT 模块可提供部分 scan 流程练习，但官方文档列明实现限制，具体能力必须按所固定版本验证。它不是完整商业 ATPG / 压缩 / MBIST / 测试签核套件。Synopsys TestMAX 官方资料用于识别工业流程的范围，产品网页不等于免费授权、教程或本人实操证据。来源见 D8、D9。

## 5. fpga：FPGA 设计 / 系统开发 / 原型验证

### 5.1 先确定 FPGA 岗位是哪一种

| 子方向 | 主要对象 | 在共享 RTL 基础上补什么 | 最有用的求职证据 |
|---|---|---|---|
| 板卡 / 工业控制 / 采集 | 外设接口、时钟、板级稳定性 | I/O 电气标准、板卡原理图、串口 / SPI 等接口、调试仪器 | 板上长时间测试、接口时序、错误统计与定位记录 |
| 算法加速 / 通信 / 图像 | 算法到定点与并行硬件 | 数值误差、DSP / BRAM 资源、吞吐与带宽预算 | 软件参考模型、误差 / 资源 / 吞吐对照 |
| ASIC 原型验证 | ASIC 子系统到 FPGA 的映射 | ASIC / FPGA 差异、时钟 / 内存替换、软件加载、分区 | 适配清单、功能回归、原型限制与调试记录 |

适合喜欢把逻辑落到真实硬件、愿意查板卡资料和做系统调试的人。暂缓信号：只喜欢仿真，不愿排查时钟、引脚与电源；只想拖 IP 却不愿读接口。两周试做可先用仿真完成 UART 收发和故障测试；有板卡时再下载并记录真实串口通信。不要把购买高价板卡当作入门条件。

典型交付：模块 / 系统规格、RTL、IP 配置清单、XDC / SDC 与引脚约束、综合 / 实现结果、bitstream、板级测试、内置逻辑分析仪捕获、资源 / 性能与稳定性报告。仅亮灯只能证明最小下载链路，不能代表系统设计能力。

### 5.2 技能目标

| 优先级 | 技能 | 建议目标 | 实际验收证据 |
|---|---|---|---|
| P0 | RTL、FSM、握手、复位、CDC 基础 | L3 | 模块自检查回归，解释跨域数据稳定性和复位释放 |
| P0 | 器件资源 LUT / FF / BRAM / DSP / 时钟资源 | L2 | 预测并核对综合资源，解释为什么推断出或没有推断出 BRAM |
| P0 | 时钟 / I/O / 引脚约束与实现时序 | L3 | 约束审查、真实实现报告、未约束路径说明，不只看综合结果 |
| P0 | 一种板级接口与硬件调试 | L3；无板先 L2 | 从仿真到板测同一规格，捕获失败数据并回到时序 / 引脚 |
| P0 | Python / C、Git、自动构建与测试 | L2 | 主机脚本驱动、自动校验与错误日志，重新构建说明 |
| P1 | 定点数与 DSP / 图像 / 通信专题 | L2–L3 | 误差模型、饱和 / 截断、流水线、带宽预算；按子方向上调优先级 |
| P1 | SoC FPGA、DMA、DDR / 高速接口集成 | L2 | 依据具体平台做系统预算与测试；明确 IP 完成部分和自己完成部分 |
| P2 | HLS、PCIe、高速收发器、部分重配置 | L1–L2 | 选择与 JD 有关的一项；不将 HLS 运行成功等同于高效硬件 |

### 5.3 前置依赖与逐步路径

依赖关系：RTL / 自检查 → 器件资源与约束 → 小接口 → 板级闭环 → 多模块 / 算法 → 高速 / 系统；若无板卡，板级能力缺口保留，不能用仿真填成 L3。

| 阶段 | 周 / 小时 | 学什么、怎么练 | 出关条件 |
|---|---|---|---|
| 1 | 第 1–3 周，35–50h | 器件结构、综合 / 实现流程、仿真 UART 或 SPI | 能解释时钟与波特率关系，自检抓到错误帧 |
| 2 | 第 4–7 周，45–65h | XDC / SDC、引脚、电压标准、时钟、reset / CDC | 下载前审查约束；没有不明来源的关键告警 |
| 3 | 第 8–12 周，60–85h | 板上接口与主机脚本、ILA / 等价调试手段 | 能复现并定位一次板上问题；无板则暂停这一项评级 |
| 4 | 第 13–19 周，85–120h | 数据通路、FIFO、定点算法或采集接口整合 | 功能、吞吐、误差、资源均有预算和结果 |
| 5 | 第 20–27 周，95–135h | 稳定性、边界、资源 / 频率取舍、作品展示 | 仿真与板测证据明确区分；环境断电后可按文档重建 |

### 5.4 三级项目

**最小项目：UART 回环与可检测错误，25–45 小时。** 建议规格 8N1、115200 baud、系统时钟按实际板卡值填写；仿真端允许设定波特率偏差、复位和错误起始 / 停止条件。验收：自检查收发数据与边界；有板时运行主机测试，记录实际字节数与错误数。失败诊断：时钟频率、分频舍入、采样点、引脚、I/O 电压标准、TX/RX 连接。公开证据：RTL、测试、约束、实现报告和有时间 / 配置说明的板测日志。无板版本名称必须含“仿真”。

**核心项目：可配置数据采集 / 流式处理平台，90–160 小时。** 建议 UART 或 SPI 输入 → FIFO → 16 位运算核 → 输出；先用数据生成器替代昂贵 ADC，明确它是模拟数据源。写清系统时钟、输入峰值速率、缓存深度、输出带宽、丢包策略和统计寄存器。验收：软件参考模型、burst 与 backpressure、长时间测试、操作中复位、满载资源和实现时序；例如计划 30 分钟稳定性测试，应报告实际完成时长及测试流量而非直接宣布可靠。失败诊断：输入平均速率低于峰值造成的缓存低估、流控错拍、时钟域、主机串口缓存或定点溢出。公开证据：系统框图、带宽预算、脚本、实现报告、板测错误率原始计数、视频与已知限制。

**进阶项目：定点 FIR / 小型图像算子 / ASIC 原型，100–180 小时。** 选一项形成深度。算法路线固定样本与参考精度，对比两种位宽或并行度；原型路线选择已有明确许可证的小模块，列出 ASIC 时钟门控、存储器、复位与 FPGA 资源的适配。验收：相同输入下的误差、吞吐、延迟、DSP / BRAM / LUT 和实现时序；有板则记录实际吞吐，不能把工具估算当实测。失败诊断：带宽瓶颈、量化误差、RAM 读延迟、IP 参数或时钟关系；公开证据：对照实验、适配表和可运行演示。使用厂商 IP 时明确自写部分，不把 IP 内核当个人成果。

### 5.5 面试与常见误区

问题与回答线索：① 为什么 HDL 里的数组不一定映射成 BRAM；② 频率提高但吞吐不变可能是什么瓶颈；③ CDC 错误为何可能仿真正常、板上偶现；④ 内部逻辑正确但串口乱码先查什么；⑤ ILA 插入为什么可能改变资源与时序；⑥ 定点位宽减少如何影响误差与资源；⑦ FPGA 原型通过能证明哪些 ASIC 行为，不能证明哪些物理特性。

常见误区：只接现成 IP，没有自己的接口规格和测试；只给演示视频无源码 / 版本 / 日志；将综合估计频率当板上性能；把所有跨域路径 false path 后视为 CDC 正确；花大量预算购买暂时用不到的高速板卡。

无商业 EDA / 无板卡时：先用开放仿真完成 RTL 与测试。厂商官方工具的免费版本、器件支持和附加 IP 授权依版本而异，安装前核对具体器件与许可，不能承诺任意板卡都免费可用。AMD 官方约束和调试文档可用于学习；开源 FPGA 工具只覆盖其明确支持的器件与功能。板卡缺失时项目结论限定为仿真 / 实现，不写“完成板级验证”。来源见 D10、D11、D12。

## 6. eda-development：EDA 软件 / 算法开发

### 6.1 适合度与实际交付

适合既愿意深入 C++ / 算法 / 数据结构，又愿意理解电路模型和工程规模的人。若更喜欢使用工具交付芯片，应优先选设计或后端；若只喜欢通用软件但完全不愿学习电路，先做两周探索再决定。EDA 岗位也包含前端编译 / 综合、仿真、形式验证、STA、布局布线、器件仿真和 CAD 流程等，不应将所有内容堆给一个学生。

两周试做：用 Python 或 C++ 表示一个有向无环时序图，算最长路径并输出关键路径；增加环检测、非法输入和最小反例。若对“为什么正确、为什么慢、如何减少内存”有持续兴趣，再进入主线。

典型交付：算法 / 数据结构实现、接口与输入模型、回归测试、可复现 bug、性能与内存剖析、基准设计集、代码评审及文档。论文或竞赛可增强表达，但必须能指出本人实现、实际测试和改进代价。

### 6.2 技能目标

| 优先级 | 技能 | 建议目标 | 实际验收证据 |
|---|---|---|---|
| P0 | C++、内存 / 生命周期、STL、构建 / 调试 | L3 | 自写中等规模模块，调试器 / sanitizer 定位问题，构建可复现 |
| P0 | 数据结构 / 算法、图遍历、复杂度 | L3 | 手算与小规模穷举交叉验证，解释最坏复杂度和输入假设 |
| P0 | 数字电路与目标 EDA 环节 | L2 | 解释所处理对象与语义，避免算法正确却电路模型错误 |
| P0 | 测试、回归、日志、Git、Linux | L3 | 每个修复有最小失败例和防回归；新环境可运行 |
| P0 | Python / Tcl 与报告 / 数据处理 | L2 | benchmark 执行、数据汇总和失败分类可自动完成 |
| P0 | 性能分析与可比实验 | L3 | CPU / 内存剖析；固定输入、版本、硬件和线程数；不只报告单次最快值 |
| P1 | 一个专题：STA / 综合 / 仿真 / 形式 / P&R | L3 | 小型算法模块或开源模块扩展，从数学假设到电路结果闭环 |
| P1 | 大代码库阅读、代码评审、开源协作 | L2–L3 | 定位真实调用链；提交独立 patch / issue 草稿，公开提交须尊重项目流程 |
| P2 | SAT / SMT、数值优化、并行计算、编译器 IR、ML for EDA | L1–L2 | 依据专题选一项；先建立正确基线，再加复杂方法 |

### 6.3 前置依赖与逐步路径

依赖关系：C++ / 数据结构 → 电路表示 → 正确性测试 → 基线算法 → profiling → 优化 → 真实开源模块。若编程基础为 L0，可在共享基础外加 8–12 周、100–160 小时；这不是“学几周 Python 就能转 EDA”的路线。

| 阶段 | 周 / 小时 | 学什么、怎么练 | 出关条件 |
|---|---|---|---|
| 1 | 第 1–5 周，60–90h | C++ 小程序、容器、RAII、CMake、调试器与测试 | 能解释对象生命周期，定位越界 / 悬空引用，构建无依赖猜测 |
| 2 | 第 6–10 周，60–90h | 图结构、拓扑序、路径算法、netlist 表示 | 小图手算 / 穷举一致，环与坏输入明确拒绝 |
| 3 | 第 11–17 周，85–125h | 选一个 EDA 专题，读接口与调用链，做最小核心项目 | 明确支持模型和不支持场景，功能可复现 |
| 4 | 第 18–25 周，95–145h | benchmark、差分测试、profiling、正确性保持的优化 | 优化有误差 / 正确性检查与运行时 / 内存代价 |
| 5 | 第 26–34 周，110–160h | 对接开源项目或扩展输入范围、评审与面试 | patch 可审阅、失败例最小化、性能结论可由他人复验 |

### 6.4 三级项目

**最小项目：教学时序图分析器，30–50 小时。** 输入是自行定义并公开的 DAG：节点、边及非负固定延时；支持多源、拓扑排序、最晚到达与关键路径；明确不含真实 Liberty 非线性延时、时钟、setup / hold、寄生与例外。验收：手算小图、随机小 DAG 与穷举交叉验证、环检测、断开节点、重复边、空输入；输出确定且可追溯。失败诊断：拓扑序错误、初始化与不可达值、浮点比较、输入解析。公开证据：输入格式、算法、测试、限制。名称用“教学最长路径 / 简化 STA”，不能叫完整 STA 引擎。

**核心项目：简化增量时序或布局优化器，100–180 小时。** 二选一。A：在上述时序图上支持修改少量边延时后的增量重算，与全量重算逐节点比较。B：在固定小网表与矩形区域中实现教学放置，目标采用明确的线长估计，约束为不重叠 / 边界 / 固定单元；说明它不包含真实可布线性和签核。验收：至少三种规模、多个固定输入 / 种子、正确性先通过再比较速度；保存所有失败；性能实验记录构建类型、线程与机器。失败诊断：A 看脏节点传播、变化方向与缓存失效；B 看目标函数 / 合法化、随机性和停止条件。公开证据：基线、优化实现、数据生成器、结果与 profiling 图，不只给一张加速倍数表。

**进阶项目：真实开源 EDA 模块改进，120–220 小时。** 从 OpenROAD / Yosys / Verilator / 其他许可清楚的项目中选一个范围窄的 bug、诊断改进、测试或性能问题；先读贡献指南和现有实现，不为凑 PR 改无意义格式。验收：固定 commit，最小复现、原版失败 / 修复版成功、相关回归、模型 / API 的兼容性说明；性能改动需验证输出正确性并报告数据分布。失败诊断：确认实际调用路径，剥离配置 / 构建 / 依赖问题，检查是否被别的阶段覆盖。公开证据：可审阅 patch、测试、benchmark 和变更说明；未被维护者合并时只能写“提交 / 准备了补丁”，不能写“已被官方采纳”。

### 6.5 面试与常见误区

问题与回答线索：① 图算法时间 / 空间复杂度为何如此；② 拓扑序算法如何检测环；③ C++ 指针生命周期与容器扩容可能导致什么 bug；④ 增量结果如何证明与全量一致；⑤ 为什么性能比较要固定构建类型和线程数；⑥ 数据集太小会导致什么误判；⑦ 你修改的功能在哪条真实调用链被执行，如何验证；⑧ Python 原型到 C++ 工程实现会遇到哪些语义和性能变化。

常见误区：只做通用算法题而不理解电路；只读论文不建立可运行基线；加上机器学习就称“智能 EDA”；比较一次最佳速度；优化忽略内存或正确性；把修改 README 等同于核心工具开发经验。

无商业 EDA 时：该方向可以大量依靠公开软件、编译器、测试和图算法训练；OpenROAD / Yosys 等代码可作为真实工程对象。开源库的许可与贡献要求必须保留；外部 patch 可能需要 CLA。真实工具源码可读并不意味着学生实现已经覆盖该工具的全部模型，也不能由一个简化算法项目推断工业规模可用。来源见 D5、D6、D13、D14。

## 7. 如何从六条路线中选主线与辅线

先把两周探索、课程基础、实验室资源、目标城市真实 JD 放在一起比较。不要用“听说薪资高 / 比较容易”替代适配判断。建议主线一条、相邻辅线一条：

| 主线 | 合理辅线 | 能复用的内容 | 需要保留的岗位专属深度 |
|---|---|---|---|
| RTL | DV 或 FPGA | RTL、协议、自检查、时序 | 微架构与可综合实现的取舍 |
| DV | RTL | 协议、模块理解、断言 | 独立模型、覆盖、缺陷闭环、验证复用 |
| PD / STA | RTL 或 EDA 脚本 | 数字时序、综合、Tcl | 约束审查、物理 / 时序问题闭合 |
| DFT | DV 或 STA | 模式验证、时序、脚本 | 故障模型、scan / ATPG 与制造测试思维 |
| FPGA | RTL 或 DSP 算法 | HDL、流水线、验证 | 器件资源、板级调试、真实系统证据 |
| EDA 开发 | STA / P&R / 综合专题 | 电路与数据结构 | 软件正确性、算法、性能与工程规模 |

每 6–8 周复核一次：有没有通过出关条件、有没有更清楚的 JD、资源缺口是否影响核心证据、毕业课题能否复用、是否需要调整主线。转向应依据完成的探索任务和阻碍记录，而不是某次 bug 调不通。

## 8. 进入实习 / 校招准备的可检查条件

这些是本 Skill 的训练检查项，不是企业统一录用线：

1. 已拿到目标方向的真实 JD，能把每条要求映射到“已有证据 / 需要补齐 / 不适用 / 暂时无资源”。
2. 至少一个核心项目达到 L3：独立解释设计、定位失败、别人可以重跑；另外一个小项目补足主项目未覆盖的技能。
3. 每项简历结果注明条件，例如“在公开教学库、指定角点与约束下”或“在某型号板卡实测”；所有数字来自日志，未测项留空。
4. 能在不看 AI 输出的情况下讲清项目 10–15 分钟，并完成一个与核心技能同类的新小题；不会把 AI 帮写的部分隐藏为个人独立完成。
5. 面试材料包含调试案例、取舍案例和协作 / 评审记录；真实缺陷与教学注入分开说明，未遇真实失败也如实记录；小而完整优于大而说不清。
6. 仍存在工具资源缺口时明确列出：例如“UVM 仅完成阅读与局部实验”“FPGA 未板测”“未执行商业签核”。规划应安排补证据机会，不得替学生改写为已完成。

## 9. 本文件的证据边界

本文件的课程排序、小时预算、项目规格和验收阈值是教育规划建议，不来自某家公司的统一招聘标准。官方工具资料仅用于核对能力范围、输入输出与限制；未开展当地职位数量、薪资、录取概率或完整公司岗位抽样调查。所有资源链接、核验日期与适用任务见 [resources-digital.md](resources-digital.md)。实际给学生制定计划时，应读取其 JD、基础与资源，对以上建议重新排优先级。
